# HdrCast 常见问题

[English](faq.md) | **简体中文**

## 连不上怎么办？

**观看** 页的面板会直接说原因。它的提示大多不管界面是什么语言都是英文，可以原样转给别人；里面把主播叫作 "the host"。[network.zh-CN.md](network.zh-CN.md) §1.2 逐条做了解释。

- **"This PC has no IPv6…" / "The host's PC has no IPv6…"**：哪一方没有 IPv6，就在哪一方的路由器里打开（[network.zh-CN.md](network.zh-CN.md) §2）；<https://test-ipv6.com> 可以自查。手机热点通常自带 IPv6，可以拿来快速试一下。
- **"Both sides have IPv6 but the path is blocked"**：关掉 VPN 和游戏加速器；路由器里有"IPv6 防火墙：阻止所有入站"之类的严格选项的话，改回默认。
- **"…the host's PC only takes IPv4 from routers that keep ports…"**：观众的路由器每个目的地换一个端口，而主播那边没开放。主播在 **防火墙** 一栏点 **放行…**，并确认自己路由器的 UPnP 开着（分享期间，主播 **开播** 页的面板会写明缺什么）。**"…although the host takes IPv4 from any port…"**：观众这边的 VPN、代理或游戏加速器截走了 UDP。
- **"Not live right now"**：对方电脑上的 HdrCast 没在运行（或者那边关了 **开放连接**）；列表每 10 s 刷新一次。**"… is full"**：达到了主播的 **同时观看人数**。
- **等待同意，"等待 … 同意你连接…"**：主播要先同意（在 **谁可以连接** 里，你这台电脑是 **询问我**），或者对方电脑还在启动采集。**"… did not let you in"**：对方拒绝了、把你的电脑设成了 **禁止**，或者刚把你断开（这时一分钟内连不回去）。**"Nobody at … answered your request"**：50 s 内没有人点 **允许**。
- **想在任何地方用自己的另一台电脑**：在那台电脑上 **开播 → 谁可以连接 → 添加电脑…** → 选这台 → **我的电脑**（先核对设备码）。之后那边什么都不用点；再在那台电脑上打开 **设置 → 通用 → 登录时自动启动 HdrCast**，每次重启后它都会在线。
- **"The signaling server cannot be reached"**：本机断网了，或者信令服务器挂了；已经在看的人不受影响。
- 能连上但**画面一直不出来**：mpv 在等第一个关键帧（最多等一个关键帧间隔，默认 1 s）。超过 10 s 的话，去主播的 **日志** 页看 `[remux …]` 几行里的报错。

## IPv6 是必须的吗？

点对点靠的是 IPv6 打洞：IPv6 没有 NAT，双方同时发包，包就能穿过两边的有状态防火墙，什么都不用设置。

没有 IPv6 时应用走 IPv4：经信令服务器的 UDP 回显得知自己的公网地址映射，再用它打洞。只要**一方**的路由器有公网 IPv4 地址并且是"开着的"（应用自己做的 UPnP 转发，加上 **防火墙** 一栏的 **放行…**），另一方就算在国内常见的对称型 NAT 后面也能连上（2026-09-25 实测：江苏电信的一位朋友连上了日本的主播）。双方都在运营商级 NAT 后面时（国内部分家宽、日本的 v6プラス / DS-Lite、澳洲部分 ISP 的 IPv4）就打不通，只能靠 IPv6。HdrCast 特意不经腾讯云中转，所以这种情况会明确告诉你，而不是悄悄绕路。同一局域网里的人不需要 IPv6（走局域网的 IPv4）。

## 腾讯云服务器会看到什么？

只看到谁在线或在直播（名字、候选地址、码率、观众数，0.3.1 起还有这台电脑的设备公钥）和加入 / 应答消息，全部用组密钥签名。它看不到组密钥和 SRT passphrase，也碰不到视频。就算有人控制了服务器，最坏也只能让人连不上，没法把观众引到别处。详见 [network.zh-CN.md](network.zh-CN.md) §6。

## 为什么没有 AV1？

ffmpeg（7.1 与 master）的 MPEG-TS 封装器不支持 AV1：会把它写成 private stream (0x06)，读回来变成 `bin_data`。点对点分发是建立在 MPEG-TS 上的（中途加入的观众靠 TS 反复发送的头信息接上），所以只能用 **HEVC Main10**。v0.1 的"直连模式"可以用 Matroska 传 AV1，但它要求一方做端口转发，已经随中继模式一起删掉了。哪天 ffmpeg 能把 AV1 封进 MPEG-TS，测试 `av1_really_cannot_be_muxed_into_mpegts` 就会开始失败，那就是重新考虑的信号。

## 为什么观众要先在 Windows 里打开 HDR？

mpv 的 HDR 直通（`--vo=gpu-next --gpu-api=d3d11 --target-colorspace-hint=yes`）只是告诉 DXGI 交换链 "我输出的是 PQ / BT.2020"，**它自己不会把 Windows 切到 HDR 模式**（以前那种"mpv 会自动帮你开 HDR"的说法，从 NVIDIA R560 驱动起已经不成立）。Windows 的 HDR 没开时，这个声明会被忽略，或者得到奇怪的画面（发灰或过暗）。用 `Win + Alt + B` 切换 HDR，或者在 设置 → 系统 → 屏幕 → 使用 HDR 里打开。**观看 → 输出 → 自动** 只在检测到 HDR 输出时才用直通，否则做色调映射，所以忘了开也不会黑屏，只是画面不是真 HDR。

静态 HDR 元数据只在**全屏**时才会送到显示器（Windows 的限制）：窗口模式也是 HDR，但显示器不会切到它的 HDR 模式。要真全屏就用 **全屏** 按钮（`--fs`，不是 `--d3d11-exclusive-fs`）。

## 观众是 SDR 显示器怎么办？

两个选择：

1. **mpv 色调映射（推荐）**：把 **观看 → 输出** 设成 **SDR**（`--target-colorspace-hint=no --tone-mapping=bt.2390`；**色调映射** 里还有别的曲线）。mpv 在 GPU 上把 PQ 映射到 SDR，观感接近主播的 SDR 桌面，高光被压缩。
2. 主播把 **开播 → HDR** 设成 **始终 SDR**：桌面按 SDR 采集（nv12 / BT.709），所有人都看 SDR，但主播自己的 HDR 桌面按 SDR 采集时亮度会被裁掉。只在观众全是 SDR 时用。

## 码率怎么选？

10 bit HEVC、60 fps、桌面和游戏混合内容的经验值：

| 分辨率 | 够用 | 好 | 极致（再高 NVENC 也没有收益） |
|---|---|---|---|
| 1920×1080 | 12 Mbps | 20 Mbps | 30 Mbps |
| 2560×1440 | 20 Mbps | 35 Mbps | 50 Mbps |
| 3840×2160 | 40 Mbps | 60 Mbps | 80～100 Mbps |

- 满是文字的桌面比游戏更吃码率（细节多）；快速运动的游戏要高码率才不糊。
- 从 4K 显示器分享游戏时，把 **开播 → 分辨率** 设成 1440p，通常比低码率的 4K 更清楚，带宽也只要一半。
- 码率上限由**主播的上行带宽 ÷ (观众数 × 1.25)** 决定，而不是想要多好的画质：见下一个问题。
- 关键帧间隔保持 1～2 s（0.3.2 起默认 1 s，**开播 → 更多选项 → 关键帧间隔**）：观众加入后要等到下一个 IDR 帧才有画面，传输中受损的画面也要停到下一个关键帧（见下文）。选 **mpv 直接播放** 时，在此之前 mpv 会刷 "Could not find ref with POC"，这是正常的。

## 开播要多少上行带宽？

主播的电脑给每位观众各发一份，所以：

```
上行需求 ≈ 码率 × 观众数 × 1.25（SRT 开销 oheadbw=25 %；oheadbw=50 % 的观众，即中国预设，按 ×1.5）
```

- 40 Mbps × 2 人 = 100 Mbps；40 Mbps × 3 人（其中一位在中国）≈ 160 Mbps。
- 先测速看看自己的上行，留 30 % 余量。不够时就降码率或减少人数，不要调低 oheadbw（Haivision 提醒过：开销留得太少，线路一丢包流就会卡死）。
- **开播** 页会按 **同时观看人数** 算出需要的上行；填上 **我的上行带宽**，估算超过它的 80 % 就会标红。**正在观看** 列表上方的 "上行 ≈ … Mbps" 是当前已连接的观众实际需要的上行。
- 国内家宽上行常见 30～100 Mbps，澳洲 NBN 常见 20～50 Mbps：那边的朋友开播给两三个人看时，码率一般要降到 10～20 Mbps。

## 画面卡顿 / 断线，按什么顺序排查？

1. 观众的播放器日志（**日志 → 播放器**）里有 `No room to store incoming packet` → 接收缓冲太小：把 **设置 → 预计最高码率** 调大（它决定 rcvbuf / ffs），见 [network.zh-CN.md](network.zh-CN.md) §4。
2. 线路丢包：观众先停止，在 **观看 → 延迟 → 自定义** 里加 500～1000 ms 再连接（主播给这位观众的那条连接就用这个值）；还不行就降码率。主播的上行不够时，所有观众会一起卡：看主播 **开播** 页 **正在观看** 列表上方的 "上行 ≈ … Mbps"。
3. 主播 **开播** 页上 **编码** 的速度一直低于 1.0×，或者 **丢帧** 一直在涨 → 编码器跟不上：降低分辨率或帧率，或者把 **更多选项 → 编码预设** 改成 **速度**。（**丢帧** 既包括编码器丢掉的帧，也包括因为 ffmpeg 没在读、采集交不出去的帧，后者一般是同一个问题。）

## 画面会停一下（以前是花屏、满屏色块）

传输中丢了数据、SRT 又没能在观众的延迟之内补发成功时，流里就少了几个包。解码器察觉不到：0.3.2 之前，受损的那一帧以及之后到下一个关键帧为止的每一帧都会花成色块。0.3.2 起，观众这边的 HdrCast 改为让画面停在最后一帧完好的画面上，等到下一个关键帧再继续（最多一个关键帧间隔，默认 1 s；声音不停），和 Moonlight 的做法一样。

- 需要 **设置 → 播放方式 → 自动（有 ffmpeg 就用）**（默认）和 HdrCast 自带的 ffmpeg：选 **mpv 直接播放** 的话，受损的画面照旧显示。**观看** 页上会显示画面定格了几次，观众的 **日志** 页里有 `[guard]` 几行。
- 线路丢包多严重：**观看** 页码率下面的 **丢包 … %**；主播 **开播** 页每位观众后面的 **途中丢包 … %** / **… 个包来不及补发**。丢包时两边的日志每 30 s 各写一行 `[net]`：观众那行里的 `…% lost on the way, n never recovered in time` 才是真正让画面受损的。
- 经常定格：观众先停止，在 **观看 → 延迟 → 自定义** 里加 500～1000 ms（或者选 **中国**，3.5 s）；"never recovered" 还是很多，就让主播降码率。主播那边 "来不及补发" 很多，说明是主播的上行或码率的问题。
- 0.3.2 起主播的编码器码率也更平稳（码率缓冲 0.25 s，原来 2 s），并且按真实的线上码率告诉 SRT，丢包本身就少了：两边都要更新。
- 停得更短（0.3.3）：主播有 NVIDIA 显卡时，打开 **开播 → 更多选项 → 按需关键帧**。这时 HdrCast 自己驱动 NVENC，装了 0.3.3 的观众丢了部分画面时马上能拿到一个新的关键帧，不用等下一个定时的关键帧：画面一般只停零点几秒，而不是最长一秒（两边的日志有 `[keyframe]` 几行）。没有 NVENC、或者在主播的电脑上用不了时，照旧由 ffmpeg 编码。

## 声音从哪里来？需要虚拟声卡吗？

不需要。Windows 上，采集引擎用 WASAPI loopback 录默认播放设备的混音（同时往它播放一路静音，免得音频引擎休眠），重采样成 48 kHz 立体声 f32，和视频用同一个 QPC 时钟对齐后，通过命名管道交给 ffmpeg；ffmpeg 编码成 192 kbps 的 AAC（或 Opus）。Mac 上的系统声音来自 ScreenCaptureKit，和画面在同一个流里。**开播 → 声音** 里有 **电脑声音** 开关，Windows 上还有 **输出设备**，可以录默认设备以外的设备。

## 大家在同一个语音里，观众会听到自己的回声吗？

主播在 **开播 → 声音 → 排除程序** 里选上语音软件（例如 `Discord.exe`；列表里是正在出声的程序，也可以手动输入名字）就不会。它和它启动的子进程的声音都不会进直播流。这和 Parsec 的回声消除用的是同一个 Windows 接口（Windows 10 21H1 或更新），一次只能排除一个程序。Mac 当主播时不能排除程序。

## 为什么采集不用 ffmpeg 自带的 ddagrab？

ddagrab 能拿到正确的 scRGB FP16 帧，但 ffmpeg 里没有任何无损的办法把打包的 FP16 交给 zscale 或 libplacebo：swscale 会把所有大于 1.0（超过 80 nit）的值裁掉（三个版本实测），HDR 就被压成了 SDR。HdrCast 用自己的 D3D11 compute shader 在 GPU 上做 scRGB → PQ / BT.2020 → P010，ffmpeg 只负责编码 P010，这也是 OBS 的做法。详见 [design.md](design.md) §1.1。

## 远程控制在有些窗口里没反应，为什么？

Windows 只让权限不低于对方的程序向对方的窗口发键盘鼠标（UAC 的"用户界面特权隔离"）。HdrCast 以普通用户的权限运行，所以前台是**以管理员身份启动**的程序的窗口时，观众的鼠标和键盘会被系统悄悄丢掉。Parsec、Sunshine 没有这个问题，是因为它们的安装程序装了一个权限更高的 Windows 服务。

HdrCast 做的是同一件事。在当主播的那台电脑上打开 **设置 → 通用 → 控制以管理员身份运行的程序**，Windows 会请求一次确认。它会把一个很小的程序 `HdrCastInput.exe` 放进 `C:\Program Files\HdrCast\Input`，并把它注册成 Windows 服务 **HdrCastInput**，用系统账户运行。服务碰不到你的桌面，所以别人控制你的电脑时，HdrCast 先启动这个服务（只有你这个用户有权启动），服务再在你的会话里启动同一个程序，由它把 HdrCast 发来的输入打出去。其余时间什么都不运行：服务不是开机启动的，最后一个观众离开约 45 秒后两个都会停。同一个开关可以再把它删掉。

- 没开时，**日志**页在发现这种情况时会写一句：*Windows refuses the viewer's mouse and keyboard right now…*。
- 这和 Parsec 的取舍一样：以你的身份运行的任何程序都能让这个程序打字，也就不经 Windows 的确认就够得到管理员窗口。它的特权全部去掉了，只打字，也只在你自己的桌面上。觉得不放心就不要开，或者让要控制的程序别以管理员身份运行。
- 不包括：Windows 的权限确认（UAC）和锁屏。它们在另一个独立的桌面上，HdrCast 的采集和输入都够不到；而且真够到了，你的任何程序都能替自己的权限确认按"是"。
- HdrCast 没有代码签名，没签名的程序注册服务，在 Windows 安全中心看来可能可疑。如果它报了 `HdrCastInput.exe`，请到 issue 里说一声，不要先点"允许在设备上"。

## 安全性如何？

- 邀请码里的 32 字节组密钥是一切的根：信令鉴权 key、消息签名 key、SRT passphrase（AES-256，`pbkeylen=32`）和每个会话的打洞 key 都由它派生。**有邀请码就能进组观看**，所以只发给信得过的人；要把某人挡在外面，就新建一个组，把新邀请码发给其余的人。
- 视频从主播的 remux 进程到观众的 mpv 全程 AES-256 加密。打洞包带 HMAC；没通过验证的地址发来的数据一律丢弃，碰不到主播电脑上的 ffmpeg。
- 0.3.1 起每台电脑还有自己的设备密钥（在 `device.json` 里：不要发给任何人，也不要拷到别的电脑上）。**谁可以连接** 里的规则认的是这把密钥，而不是组里谁都能填的名字；两台 0.3.1 电脑之间的远程控制输入，用只有这两台算得出来的密钥加密。
- 信令服务器只看到签名的元数据（见上面的"腾讯云服务器会看到什么？"）。

## 界面上的 "ping 38 ms" 是延迟吗？

不是。那是打洞路径的往返时间（网络 ping）。画面延迟 ≈ 观众的 SRT 延迟 + 播放器缓冲（1.5 s，**设置 → 播放器缓冲**）+ 编解码（约 0.5 s）：日本预设实测 3.6 s（2026-09-24，一台电脑走本机回环，[network.zh-CN.md](network.zh-CN.md) §3），中国预设约 5.6 s。SRT 延迟是重传的时间窗口：它决定能扛多少丢包，**不决定画质**；画质只看码率和编码预设。线路好的时候，长延迟和短延迟看起来一样，只是一个晚几秒。

## 延迟能再低一点吗？

要操作对方的电脑，可以：用 **控制模式** 连接（0.3.7，**观看 → 连接 → 模式 → 控制**）。和 Moonlight 一样什么都不缓冲、什么都不重发：同一台电脑上 120 fps 从屏幕到屏幕实测，画面 1080p 只晚 14.5 ms、4K HDR 晚 21 ms，真实网络上再加单程的网络延迟。主播要有 NVIDIA 显卡，线路要好：丢了一帧画面会停到关键帧来，丢包多的线路上就会常停（见 README 的「控制模式」一节）。

观看是按直播来设计的。在 **观看 → 延迟** 里选 **快速**（300 ms），或者 **自定义** 成约 4 × RTT（日本约 200 ms、澳洲约 700 ms），再把 **设置 → 播放器缓冲**（mpv 的 `cache-pause-wait`）调到 0.5 s：总延迟能降到 1.5 s 左右，但线路一抖画面就会卡。不建议低于 3 × RTT。
