# HdrCast 网络说明

[English](network.md) | **简体中文**

HdrCast 是**点对点**的：主播的电脑直接把流发给每位观众，腾讯云上的信令服务器只负责牵线。本文说明它怎么穿过路由器和防火墙、谁需要什么、怎么自查 IPv6、各地区的 SRT 延迟预设、缓冲公式和上行带宽。协议本身见 [design.md](design.md) §8。

## 1. 点对点怎么连上

```
 主播            hdrcast-signal              观众
                   （腾讯云）
  │                     │                     │
  │────────────────────►│                     │   1. 在线，候选地址 [IPv6]:51234
  │                     │◄────────────────────│   2. 谁在线？（每 10 s 问一次）
  │                     │◄────────────────────│   3. 加入，候选地址 [IPv6]:40000
  │◄────────────────────│                     │   4. 有人要看
  │────────────────────►│────────────────────►│   5. 应答：好，候选地址…（服务器转给观众）
  │                     │                     │
  │◄═════════════════════════════════════════►│   6. 双方每 100 ms 互发 PUNCH，收到就回 PUNCH_ACK
  │◄═════════════════════════════════════════►│   7. SRT（AES-256）走同一条 UDP 路径
```

服务器只存几百字节的签名元数据，从不转发视频；第 4 步是 long poll，有人加入就立刻返回。第 6 步里，两边的有状态防火墙都看到"自己先发出去了"，于是放行对方的回包。第 7 步 SRT 的两端在两台电脑上都只连本机：主播的 remux ffmpeg (127.0.0.1) ⇄ HostLink ⇄ 打通的路径 ⇄ ViewerLink ⇄ mpv (127.0.0.1)。

- **为什么 IPv6 能打洞**：IPv6 没有 NAT，每台电脑都有全球地址和固定端口。家用路由器、光猫和 Windows 防火墙对 IPv6 都是"有状态"的：挡住没人请求过的入站，放行"自己先发出去"那条流的回包。双方同时向对方发包，两边都算自己先发，于是都放行对方。**谁都不用做端口转发，也不需要公网 IPv4。**
- **候选地址**：IPv6 用通往互联网的那块网卡上的**稳定**地址。Windows 默认用临时地址发包，但临时地址每天都变，而且发包的地址必须就是公布出去的那个，所以 socket 直接绑在稳定地址上。IPv4 候选是：局域网地址（给同一局域网里的人）、经信令服务器 UDP 回显得到的公网映射，以及路由器用 UPnP 转发的端口（§1.1）。
- **学来的地址**：对方的包从一个它没公布过的地址和端口来时（对称型 NAT 给每个目的地新开一个端口），这个地址也成为打洞目标：对方的 NAT 正是为我们开的这个口子，往这里发的包进得去。
- **选路**：先收到 ACK 的路径胜出；如果 IPv4 先通，HdrCast 再等 200 ms，IPv6 也通的话就改用 IPv6。主播跟着观众的选择走。
- **每位观众一条 SRT 连接**：主播给每位观众各起一个 remux ffmpeg（`-c copy`，不重编码），按**这位观众**的延迟和 oheadbw 重传，所以谁的网络差只影响谁。
- **在线 / 开播（0.3.1）**：两种情况下第 1 步都一样。HdrCast 在运行、**开放连接** 打开时，这台电脑就向组里宣告自己"在线"，等有人被放进来才开始采集屏幕。这时主播端先启动采集和编码器再应答（通常 1～2 s），好让观众的 mpv 一连上就有画面；最后一位观众离开 20 s 后两者都停掉。主播对这位观众的规则是 **询问我**、且主播没在直播时，应答要等主播点 **允许**（最多 50 s）。**开始直播** 则把这台电脑宣告为正在直播，编码器一直开着。
- **断线重连**：一条路径 15 s 没有任何包就算断开，观众端会自己重新加入（用同一个本地端口，mpv 不用重启就能接上）。主播停止时会发 BYE，观众的面板上显示 "The stream ended - waiting for … to go live again"（那台电脑只是在线时显示 "… ended the session - asking again"）。

### 1.1 谁需要什么

| | 主播 | 观众 |
|---|---|---|
| IPv6 | 双方都有最省事：下面几行都不用管 | 同左 |
| 公网 IPv4 | 没有 IPv6 时，至少一方的路由器要有公网 IPv4 地址（不是 10.x / 100.64～127.x / 172.16～31.x / 192.168.x） | 同左 |
| 路由器端口转发 | 不用手动做：HdrCast 在线或直播期间会自己用 UPnP 转发它的 IPv4 端口，停下时删除（路由器要开着 UPnP，大多默认开） | 同左（观看期间） |
| Windows 防火墙 | 应用里 **防火墙** 一栏出现 **放行…** 时点它（Windows 要管理员确认一次；放在新文件夹里的新版本要再点一次；macOS 不需要） | 同左（只有主播在对称型 NAT 后面时才用得上） |
| 上行带宽 | 码率 × 观众数 × 1.25～1.5（§7） | 很少（只有 ACK） |
| 下行带宽 | 很少 | 码率 × 1.3 |

没有 IPv6 的一方只能走 IPv4，条件是：

1. **信令服务器的 UDP 18651 是开着的**（§6）。公网 IPv4 候选只能靠这个回显得到。不通的话主播只公布 IPv6 和局域网地址，观众根本没有 IPv4 地址可试（主播日志：`public IPv4 check: no answer…`；主播 **开播** 页的面板：`no public IPv4 found`）。
2. **路由器保持端口，或者有一方是开着的**：
   - **锥形 NAT**（同一个内网端口发往任何目的地都用同一个公网端口，家用路由器大多是）：双方同时往对方的公网映射发包，路由器和 Windows 防火墙都放行回包，什么都不用开。
   - **对称型 NAT**（每个目的地换一个公网端口：国内运营商和运营商级 NAT 常见）：它发出的包来自一个对方没见过的端口，对方的路由器和 Windows 防火墙会当成"没请求过的包"丢掉。这时**另一方**必须收得下这种包：路由器上的 UPnP 转发（HdrCast 自己会做）加一条 Windows 防火墙规则（点 **放行…**）。只要有一个包进来，HdrCast 就记下真实端口并反过来往那里打洞（design.md §8.6），所以谁当主播都行，只要另一方是开着的。**双方都在对称型 NAT 后面时 IPv4 过不去**：至少一方要有 IPv6。
   - 实例（2026-09-25）：一位朋友（江苏电信，没有 IPv6）公布的端口是 :20833，包到主播那里却来自 :20834。主播这边只有防火墙规则时，网卡上一个包都没收到（全被路由器丢掉了）；路由器的 UPnP 转发一加上，不到一秒就连上了。

### 1.2 连不上时各条提示的意思

除非第一列写了别的地方，下面都是 **观看** 页面板上的提示。大多数来自连接引擎，不管界面设成什么语言都是英文（出问题时大家发来的日志里也是这些话），里面把主播叫作 "the host"。

| 提示 | 含义 / 怎么办 |
|---|---|
| This PC has no IPv6 internet connection, and the host offered no public IPv4 address… | 本机没有 IPv6，主播也没公布公网 IPv4 地址（主播那边的 UDP 回显没有回复，§1.1 第 1 条），所以根本没试 IPv4：在本机按 §2 打开 IPv6，或者先在信令服务器上放行 UDP 18651 |
| This PC has no IPv6 internet connection, and the IPv4 attempt did not get through… | 本机没有 IPv6，IPv4 打洞也没成功（至少有一方的 NAT 不配合，§1.1 第 2 条；后面还写着 *this PC's public IPv4 address could not be found* 的话，本机连自己的公网 IPv4 都没拿到）：按 §2 打开 IPv6 |
| …did not get through: the host's PC only takes IPv4 from routers that keep ports… | 主播的 IPv4 没开放（路由器没转发，或者防火墙没规则），而本机的路由器多半是对称型 NAT：请主播点 **放行…**，并确认主播的路由器开着 UPnP；或者在本机打开 IPv6 |
| …did not get through although the host takes IPv4 from any port… | 主播那边是开放的，包却没到：本机的 VPN / 代理 / 加速器（Clash TUN、UU 之类）截走了 UDP。关掉它，或者让 HdrCast 绕过它 |
| 主播 **开播** 页的面板：`IPv4 closed to routers that change ports: …` | 主播的 IPv4 没开放，冒号后面写了缺什么：`no router forward (UPnP)` → 在路由器里打开 UPnP；`no firewall rule (click Allow)` → 点 **放行…**；`router behind another NAT` → 路由器外面还有一层 NAT（路由模式的光猫，或者运营商级 NAT），转发帮不上忙 |
| 日志：`[p2p] router: could not forward UDP …` | 路由器没开 UPnP，或者拒绝了转发：原因写在短横线 `-` 后面（被拒绝时会附上路由器的错误码）。HdrCast 一分钟后重试，之后间隔越来越长；打开 UPnP 后不用重启 HdrCast |
| 主播日志：`connected via IPv4 … (a port their router picked for this PC …)` | 对方在对称型 NAT 后面，是通过这边打开的 IPv4 端口进来的：一切正常 |
| 主播日志：`left (could not connect: no candidate answered; …)` | 对方的包一个都没到。分号后面是可能的原因：这边的 IPv4 已经开放的话，是对方那边有东西截走了 UDP；没开放的话，先按提示打开 |
| The host's PC has no IPv6 internet connection… | 主播没有 IPv6：请主播按 §2 打开 |
| Neither side has IPv6… | 双方都没有 IPv6，IPv4 也没通：至少一方要有 IPv6 |
| 主播 **开播** 页的面板：`no public IPv4 found`；日志：`public IPv4 check: no answer…` | 信令服务器的 UDP 18651 没有回复：在腾讯云安全组里放行（§6）。主播端每分钟重试一次，观众端每次加入前都会重试，所以放行之后谁都不用重启 |
| Both sides have IPv6 but the path is blocked… | 双方都有 IPv6，包却过不去：多半是 VPN（关掉），或者路由器里"IPv6 防火墙：阻止所有入站"之类的严格设置（改回默认 / 标准） |
| 等待同意：等待 … 同意你连接… | 主播要先放这台电脑进来（主播对它的规则是 **询问我**，看到的请求上带着这台电脑的设备码），或者对方电脑还在启动采集 |
| … did not let you in | 主播点了 **拒绝**、把这台电脑设成了 **禁止**，或者不到一分钟前刚断开过它。HdrCast 不再重试：去问问主播 |
| Nobody at … answered your request | 50 s 内没有人点 **允许** |
| Not live right now / 现在没有人在线 | 对方电脑上的 HdrCast 没在运行（或者那边关了 **开放连接**）；列表每 10 s 刷新一次 |
| … is full | 达到了主播设的 **同时观看人数** |
| The signaling server cannot be reached | 本机断网了，或者信令服务器挂了；已经在看的人不受影响 |

## 2. IPv6 自查与开启

1. 打开 <https://test-ipv6.com>：看到 "IPv6 address detected"（最好是 10/10）就行。
2. 没有的话，一般是路由器或光猫没开：
   - **日本**：NTT フレッツ系、SoftBank 光、au ひかり 的线路默认都有 IPv6（IPoE）；SoftBank 的 光BBユニット 默认开着 IPv6。
   - **中国**：三大运营商的家宽基本都已下发 IPv6，但不少光猫和路由器默认只开 IPv4。在路由器里找"IPv6 设置"、"IPv4/IPv6 双栈"或"IPv6 模式"打开（光猫桥接的话在你自己的路由器上开）；手机热点通常自带 IPv6，可以先用热点试试。
   - **澳洲**：看 ISP。一部分 NBN ISP 默认给 IPv6，另一部分不提供；不提供的话只能换 ISP，或者让组里有 IPv6 的人来开播。
3. Windows 里 IPv6 默认是开着的；装了 VPN 或加速器的话，先关掉再测。

## 3. 各地区延迟预设与理由

观众在 **观看 → 延迟** 里选预设。这个值随加入请求发给主播，主播为这位观众起的 remux 进程就用它（中国预设同时把 oheadbw 提到 50 %）。所以同一场里，日本观众 1.5 s、中国观众 3.5 s 可以各得其所。这些预设是按主播在日本来定的：

| 观众所在地 | RTT（估计） | 丢包 | SRT 延迟 | oheadbw |
|---|---|---|---|---|
| 日本 | 10～30 ms | ≈0 | **1500 ms** | 25 % |
| 澳大利亚 | 120～160 ms | 少量 | **2000 ms** | 25 % |
| 中国大陆（跨境） | 60～120 ms，但抖动和突发丢包多 | 常见 1～5 % | **3500 ms** | 50 % |

**快速**（300 ms，oheadbw 25 %）是给远程控制用的：画面跟得很紧，但留给重传的时间很少，所以要求线路干净、距离近。选 **自定义** 时，3000 ms 及以上的延迟会像中国预设一样要求 oheadbw 50 %，更短的是 25 %。

理由：

1. **Haivision 的 4 × RTT 规则**：SRT latency = RTT 乘数 × RTT；在丢包 0.1～0.2 %、没有突发的"还不错"的网络上，乘数约为 4。低于 3 基本没有意义，高于 20 说明线路已经严重拥塞。
2. **官方保守表**（丢包率 → 乘数 / 带宽开销）：≤1 % → 3 / 1 %；≤3 % → 4 / 4 %；≤7 % → 6 / 9 %；≤10 % → 8 / 15 %；≤12 % → 8 / 20 %；≤21 % → 10 / 38 %；≤25 % → 13 / 46 %；≤30 % → 14 / 61 %；≤40 % → 30 / 97 %。
3. 按 4 × RTT 算，澳洲只要约 640 ms，中国只要约 480 ms。但目标是直播，不是远程桌面：多留几倍余量能扛住跨境线路的突发丢包（重传要在延迟之内到达），代价只是延迟大一点。中国线路按丢包 3～7 % 取乘数 6～8，再留余量，得到 3500 ms；`oheadbw` 也提到 50 %，给重传留带宽。
4. 延迟由两端协商，取**较大**的值（发送端的 `peerlatency` 对接收端的 `rcvlatency`）。两端都用观众的值，所以观众选的就是生效的值（实测：API 里的 `msReceiveTsbPdDelay` / `msSendTsbPdDelay` 正好等于 URL 里的值）。
5. 端到端延迟 ≈ 接收端的 SRT（1.5～3.5 s）+ mpv 的 `cache-pause-wait`（**设置 → 播放器缓冲**，1.5 s）+ 编码（约 0.4 s），即日本约 3.5 s、中国约 5.5 s。2026-09-24 在一台电脑上走本机回环实测（NVENC → SRT 1500 ms → mpv 用观众端的原样参数；画面里烧进 UTC 时间戳，经 IPC 截图对比）：**3.58 s**，三次一致，mpv 的 `demuxer-cache-duration` 稳定在 1.55 s。界面上的 "ping 38 ms" 是网络往返时间，不是画面延迟。
6. 延迟决定的是能扛多少**丢包**（重传窗口），不是画质：线路好时 1.5 s 和 3.5 s 画面一样，只是一个晚两秒；画质只取决于码率和编码预设。在中国跨境观看的人应该选中国预设（3500 ms、oheadbw 50 %），不然偶尔丢的包重传赶不上，画面就会花。

> 观众可以自己调：画面老是卡（mpv 反复缓冲）就先停止，在 **观看 → 延迟 → 自定义** 里加 500 ms 再连接；线路好就往下减。

## 4. 缓冲大小公式（必须做，否则高码率会断线）

libsrt 默认的接收缓冲只能放 8192 个包（约 10.8 MB）。延迟 × 码率超过它时，重传窗口里放不下的包会被丢掉：画面花屏，甚至整个断线（在一台电脑上 48 Mbps × 2 s 就能复现）。所以两端都按下面的公式把参数写进 URL（实现在 `crates/core/src/common/srt_buffer_sizing.rs`）：

```
packets = ceil( latency_s × bitrate_bps / (1316 × 8) )      # 每个 SRT 包 1316 字节载荷
ffs     = max( 25600, 大于等于 packets × 1.2 的最小 2 的幂 )   # SRTO_FC，流控窗口（单位：包）
rcvbuf  = ffs × 1472                                          # SRTO_RCVBUF 必须 ≤ ffs × (MSS − 28)
sndbuf  = 同 rcvbuf（发送端）
recv_buffer_size = 8000000                                    # UDP socket 缓冲（Linux 上受 net.core.rmem_max 限制，会被静默截断）
```

例子：

| 码率 × 延迟 | packets | ffs | rcvbuf |
|---|---|---|---|
| 40 Mbps × 1.5 s | 5 700 | 25 600（默认） | 37 683 200 |
| 50 Mbps × 2 s | 9 499 | 25 600 | 37 683 200 |
| 100 Mbps × 2 s | 18 997 | 25 600 | 37 683 200 |
| 100 Mbps × 3.5 s | 33 245 | 65 536 | 96 468 992 |

观众不知道主播会用多大码率，所以按 **设置 → 预计最高码率** 来定缓冲大小（默认 100 Mbps；宁大勿小，多占的只是内存）。

## 5. 防火墙要开什么

- **双方都有 IPv6，或者都在锥形 NAT 后面**：什么都不用开。打洞靠的就是路由器和 Windows 防火墙放行"自己先发出去的流"的回包。
- **有一方在对称型 NAT 后面**（§1.1 第 2 条）：另一方要收得下"没请求过的"UDP，下面两样都要：
  - **路由器**：HdrCast 自己用 UPnP 把当前的 IPv4 端口转发到这台电脑。租期 1 小时，HdrCast 在线、直播或观看期间每 20 分钟续一次，停止时删除；HdrCast 崩溃的话，转发最多一小时后自己失效。日志里是 `[p2p] router: …` 这几行。路由器设置里 UPnP 要开着（大多默认开）。
  - **Windows 防火墙**：**防火墙** 一栏出现 **放行…** 时点它（在 **开播** 页：缺这条规则时在最上面，平时在 **观众** 下面；以及 **设置 → 网络** 里）。Windows 弹出 UAC 确认后，会加一条入站规则"HdrCast"：只对这个 exe、只限 UDP、所有网络类型（0.2 的两条规则 "HdrCast Sender" 和 "HdrCast Receiver" 可以留着）。以前在 Windows 弹窗里点"取消"留下的阻止规则会被停用，不会被删除。还没有这条规则时，只要这台电脑能被连接（**开放连接** 打开，或者点了 **开始直播**），HdrCast 每次运行都会问一次；观众在 IPv4 尝试失败、而这条规则能帮上忙时，也会被问一次。
  - 规则认的是 exe 的完整路径：放在新文件夹里的新版本（比如 `D:\HdrCast-0.3.1\`）要再点一次。撤销：Windows 安全中心 → 防火墙和网络保护 → 高级设置 → 入站规则，删掉这条。
- **安全吗？** 开的只是 HdrCast 自己的一个 UDP 端口。HdrCast 只接受用组密钥签名的打洞包和来自已确认地址的数据，其余一律丢弃；视频本身用 SRT 的 AES-256 加密。

## 6. 腾讯云上的信令服务器做什么

`signal/hdrcast_signal.py`（只用 Python 标准库，由 systemd 运行，见 [signal/README.zh-CN.md](../signal/README.zh-CN.md)）：

- **存什么**：每个组里谁在线或在直播（名字、设备公钥、候选地址、码率、观众数；30 s 不续期就过期）、加入请求和应答（60 s 后过期），以及组 id → 鉴权 key 的注册表（唯一写到磁盘上的东西）。
- **看不到什么**：组密钥、SRT passphrase、视频。每条消息都用由组密钥派生的 key 签名，服务器不知道这个 key，所以就算有人控制了服务器，也只能让人连不上，没法把观众引到别处。
- **流量**：每台在线或在直播的电脑每 10 s 发一个几百字节的心跳，每个运行中的 HdrCast 每 10 s 查一次列表。和视频比可以忽略不计，也不影响那台机器上的生产服务。
- **端口**：TCP 18650（HTTP API）和 UDP 18651（IPv4 地址回显），都要在腾讯云安全组里放行。只有所有人都有 IPv6 时，UDP 18651 才可以不开：不开的话谁都拿不到公网 IPv4 映射，没有 IPv6 的观众根本连不上（§1.1）。
- **挂了会怎样**：已经连上的人照常看；新的人加入不了，列表也刷不出来；服务器恢复后一切自动继续。

## 7. 上传带宽估算

```
主播需要的上行 ≈ 码率 × 观众数 × (1 + oheadbw)      # oheadbw 25 % → ×1.25，中国观众 50 % → ×1.5
```

例：40 Mbps，日本、澳洲、中国各 1 人 ≈ 40 × (1.25 + 1.25 + 1.5) = 160 Mbps 上行。日本的光纤上行一般够用；国内家宽上行常见 30～100 Mbps，澳洲 NBN 常见 20～50 Mbps，所以那边的朋友开播时要降码率或减少人数。**开播** 页会按 **同时观看人数** 估算上行，填了 **我的上行带宽** 之后，估算超过它的 80 % 就会标红。
